### Metal 백엔드 확인 경로

Homebrew 빌드는 `libggml.dylib`에 Metal이 정적 링크되어 있지 않고,
`/opt/homebrew/Cellar/ggml/0.18.1/libexec/libggml-metal.so`를 **런타임에 동적 로드**한다.
Core ML(ANE) 지원은 없다 — 필요하면 `-DWHISPER_COREML=1`로 소스 빌드해야 하며 인코더 3x+ 추가 가속을 기대할 수 있다.

### 한국어 품질 (정성 평가)

✅ 양호. 교정이 재작성 수준이 될 거라는 우려는 이 샘플 기준 기우였다.

- 세그먼트가 발화 단위로 적절히 분할됨
- 숫자 정확: `10년`
- 긴 복문 깨끗함: "부스 밖에 있는 플레이어는 잠시 후 제시되는 문장을 입 모양을 통해 부스 내부에 있는 플레이어에게 알려주세요"

## 3. 엔진 선택 — whisper.cpp vs faster-whisper

Context7로 공식 문서 조사.

| | faster-whisper (Hermes `local`) | whisper.cpp (`whisper-cli`) |
| --- | --- | --- |
| 런타임 | CTranslate2 | ggml |
| Apple GPU | **없음 — CPU 전용** | **Metal ✅** |
| 근거 | 공식 저장소의 유일한 Dockerfile이 `nvidia/cuda` **x86_64**. ARM64 빌드 미제공. 모든 GPU 예제가 `device="cuda"` | 이 머신에서 `libggml-metal.so` 동적 로드 확인 |
| 추가 가속 | — | Core ML(`-DWHISPER_COREML=1`) → ANE, 인코더 3x+ |
| 모델 포맷 | CTranslate2 디렉토리 (HF 자동 다운로드) | GGML `.bin` |

Hermes 소스가 자체적으로 이를 뒷받침한다:
`agent/transcription_provider.py`, `tools/transcription_tools.py`의
`_should_force_faster_whisper_cpu()`, `WhisperModel(model_name, device="cpu", compute_type="int8")`.

**결론**: M4 Mac mini에서는 whisper.cpp가 맞다. `technical-foundation.md` 3절의 판단이 옳았고 근거도 정확했다.

## 4. 화자 분리 (diarization) — 앞선 판단 정정

`whisper-cli`에 diarize가 **2종** 있다.

| 플래그 | 방식 | 한국어 |
| --- | --- | --- |
| `-tdrz` tinydiarize | 모델 추론 | ❌ `small.en-tdrz` 전용 = **영어만** |
| `-di` `--diarize` | **스테레오 좌/우 채널 분리** | ✅ **언어 무관** |

`-di`가 이 제품에 맞는다. 온라인 회의 수집이 `mic.webm` + `remote.webm`을 **따로** 저장하므로,
두 트랙을 좌/우 채널로 합치면 `나` vs `원격`이 **물리적으로** 구분된다. 모델 추측이 아니라 채널이라 오분류가 없다.

| 입력 모드 | 화자 구분 |
| --- | --- |
| 온라인 (mic + remote) | `나` / `원격` 자동 ✅ · 원격 내부 다중 화자는 `참석자 N`·`미확인` 후 사용자 지정 |
| 대면 (mic만) | 채널 분리 불가 → 전부 사용자 지정 |

`review-contract.md`의 `나` / `참석자 1` / `미확인` 계약과 이미 정합한다.
ElevenLabs 등 외부 diarization API로 오디오를 내보낼 필요가 없다.

**검증 완료 (8.2절)**: 정답을 아는 합성 2트랙으로 시험한 결과 **세그먼트 정확도 98.2%(54/55), 불확실 0건**.
JSON에 `speaker` 필드가 추가된다. 단 합성에 **말겹침이 없으므로** 동시 발화 구간은 실녹음으로 재확인해야 한다.

## 5. Hermes 프로그래밍 호출 경로

`technical-foundation.md` 8절은 후보로 ACP · TUI gateway · OpenAI-compatible API server 셋을 열거했으나,
실제로는 **4개 이상**이며 성격이 다르다.

| 경로 | 실체 | Ratatouille 적합성 |
| --- | --- | --- |
| **`hermes -z "프롬프트"`** | 원샷 서브프로세스, stdout 반환 | ✅ 가장 단순. 검증됨 |
| `hermes serve` | **JSON-RPC/WebSocket 게이트웨이** (기본 127.0.0.1:9119) | 문서에 없던 후보. run 상태·event 관측에 유리할 가능성 |
| `hermes acp` | 에디터 통합(VS Code, Zed, JetBrains)용 | 제품 용도와 불일치 |
| `hermes proxy` | OpenAI 호환 요청을 OAuth provider로 **포워딩** | ⚠️ **profile·skill 층을 우회**한다. `technical-foundation.md` 2절의 "Ratatouille은 모델을 직접 호출하지 않는다" 계약과 충돌 |

**주의**: 문서가 "API server가 자연스러운 후보"라고 적었지만, `hermes proxy`는 Hermes의 profile/skill 실행을 거치지 않는
단순 포워더다. 이걸 고르면 소유권 경계가 깨진다.

### STT provider 구조

`~/.hermes/config.yaml`:

```yaml
stt:
  enabled: true
  provider: local          # ← 기본값. faster-whisper = 이 머신에서 CPU 전용
  local:
    model: base            # ← 한국어에 부족한 크기
  openai:     { model: whisper-1 }
  mistral:    { model: voxtral-mini-latest }
  elevenlabs: { model_id: scribe_v2, diarize: false }
```

내장 백엔드 6종: `local`(faster-whisper), `local_command`, `groq`, `openai`, `mistral`, `xai`.
`local_command`는 `HERMES_LOCAL_STT_COMMAND` 환경변수로 **임의의 shell 명령**을 STT로 꽂는 escape hatch다.

~~**권장 구성** — `stt.provider: local_command` + `HERMES_LOCAL_STT_COMMAND`~~

> ⛔ **이 권장은 8.3절에서 철회됐다.** `local_command`는 `.txt`만 읽어가므로 **timestamp가 소실된다.**
> 플러그인 provider ABC와 HTTP endpoint도 마찬가지다. 자세한 내용과 대안은 **8.3절** 참조.

## 6. Hermes 4개 결과 추출 실측

### 조건

- 입력: 위 전사문 153 세그먼트에 `[segNNN HH:MM:SS]` evidence ID 부여 (프롬프트 총 9,197 bytes)
- 호출: `hermes -z "$(cat prompt.txt)"` — 원샷, 도구 없음
- 프롬프트 규칙: 없는 사실 금지, 제안과 결정 구분, 미언급 담당자·기한은 `미입력`, 항목 없으면 빈 배열, 모든 항목에 실재 segID 필수

### 측정값

| 항목 | 값 |
| --- | --- |
| 소요 시간 | **28.7초** |
| JSON 파싱 | **1회 성공** (앞뒤 설명문 없이 순수 JSON) |
| 산출 | summary 1 · decisions 2 · tasks 4 · evidence 10 |

### evidence 정확도 — 최대 리스크였고, 통과했다

| 검증 | 결과 |
| --- | --- |
| evidence 배열 10건의 **segID 실재** | ✅ 10/10 |
| evidence 배열 10건의 **timestamp 일치** | ✅ 10/10 (문자열 완전 일치) |
| evidence 배열 10건의 **quote 원문 일치** | ✅ 10/10 (문자열 완전 일치) |
| 전 section이 인용한 고유 segID 18개의 실재 | ✅ 18/18 |
| **환각된 ID·timestamp·인용** | **0건** |

`GOAL.md`에서 "가장 의심스럽다"고 지목했던 evidence ID + timestamp 연결은 **실측에서 문제없었다.**
Phase 6의 화면 설계를 다시 할 필요가 없다.

### 발견된 결함 2건

#### ❌ 결함 A — evidence 배열이 인용의 부분집합

summary·decisions·tasks가 인용한 18개 segID 중 **8개가 `evidence` 배열에 없다**
(`seg037 seg038 seg043 seg085 seg115 seg117 seg127 seg128`).

`review-contract.md`는 "원문 근거는 전용 조회 영역이며, 다른 세 결과에서도 같은 segment로 이동할 수 있어야 한다"고 요구한다.
현재 출력대로면 **8개 링크가 깨진다.**

→ **조치**: 서버의 schema validator가 "모든 인용 segID ⊆ evidence 배열"을 강제해야 한다.
모델 프롬프트 개선이 아니라 **검증 규칙**으로 막을 문제다.

#### ❌ 결함 B — 제안을 결정으로 승격 (2건 중 1건)

| 결정 | 근거 원문 | 판정 |
| --- | --- | --- |
| "입 모양 읽기 게임을 다시 하기로 함" | seg088 "이거 다시 해볼까?"(제안) → seg089 "그래, 재밌겠다."(동의) → seg090 "내가 부스 안에 들어갈게."(역할 배분) | ✅ **정당** |
| "앞으로도 계속 만나기로 함" | seg151 "우리 앞으로도 지금처럼 이쁘게 만나자."(제안) → seg152 "응?"(되묻기) | ❌ **동의 발화 없음. 제안에서 끝남** |

`review-contract.md` 결정 사항 루브릭의 첫 항목 "실제 결정과 단순 제안·논의가 구분됐는가?"가
**정확히 이 오류를 잡으라고 존재한다.** 루브릭이 행정 절차가 아니라 실제 품질 도구임이 증명됐다.

→ **조치**: 루브릭 검수를 유지한다. AI 1차 판정만으로 `current` 승격을 허용하면 안 된다는 계약이 실측으로 뒷받침됨.

### 담당자·기한 — 지어내지 않았다 ✅

`tasks[1]` "파일 다시 보내기 / assignee 이영미 / due 즉시"를 원문 대조:

```
[seg037] 이영미 씨, 정신 나갔어?
[seg038] 이 파일이 아니잖아.
[seg039] 당장 다시 보내.      ← due "즉시"의 근거
[seg040] 아, 네.              ← 이영미의 수락 = assignee 근거
```

담당자와 기한 모두 발화 근거가 있다. 나머지 3개 task는 기한 미언급 → 전부 `미입력`으로 정확히 반환했다.
**없는 기한·담당자를 만들어내는 실패 모드는 관측되지 않았다.**

### 한계

- 이 샘플은 **회의가 아니라 방탈업 게임 상황극**이다. 실제 회의의 결정·Action Item 밀도, 전문 용어,
  다중 화자 겹침에서 같은 정확도가 나온다고 일반화하지 않는다.
- 1회 실행 결과다. 재현성(같은 입력에 대한 출력 안정성)은 측정하지 않았다.
- Hermes `ratatouille` profile과 skill을 쓰지 않고 원샷 프롬프트로만 시험했다.

## 7. 모의 회의 실측 (2차) — 정답을 심어둔 검증

**샘플**: `회의음성.mp3` — 600초(10분), mp3 192kbps, stereo 44.1kHz
**대본**: [`MOCK-MEETING-SCRIPT.md`](../MOCK-MEETING-SCRIPT.md) — 결정·Action Item·함정을 미리 심어 정답 대조 가능
**채널**: 좌우 차이 평균 -36.2dB (원본 -20.7dB) → **2트랙 분리 녹음 아님.** `-di` 화자 분리는 이번에도 미검증

### 7.1 성능

| 항목 | 회의음성 (600초) | 1차 샘플 (507초) |
| --- | --- | --- |
| 전사 소요 | **47.2초 → 12.7x 실시간** | 34.9초 → 14.5x |
| 백엔드 | Metal ✅ | Metal ✅ |
| 피크 메모리 | **2.09 GB** | 1.98 GB |
| 세그먼트 | 154 | 153 |
| 4개 결과 추출 | **41.9초** | 28.7초 |
| **전체 체인** | **89초** | 64초 |

### 7.2 전사 정확도 — 발화 단위 70.2%

⚠️ **채점 방식 정정**: 1차 채점기는 "한 번이라도 맞으면 통과"라 17/17(100%)로 나왔다.
**발화 단위로 세면 33 정확 / 14 오류 = 70.2%**다. 아래가 정확한 수치다.

| 대상 | 정확 | 오류 | 오표기 |
| --- | --- | --- | --- |
| **숫자·날짜 12종** | **12** | **0** | — |
| 토스페이먼츠 | 2 | **5** | 토스페이먼**치**×4, 토스페에서×1 |
| 그라파나 | 0 | **2** | 그래파나×2 |
| 이한결 | 3 | 2 | 한결**시**×2 |
| PG사 | 3 | 2 | 피지사×2 |
| 나이스페이 / QA / SLA / API | 16 | 0 | — |
| 재시도 / 저장소 / 안건 | 6 | 3 | 제시도, 저장족, 만건 |

**패턴: 숫자·날짜는 완벽, 고유명사는 취약.**
의도적으로 가까이 붙인 `3월 2일` / `3월 5일` / `3월 16일`이 **전혀 섞이지 않았고**,
`2.8%` · `15일` · `460만 원` · `24시간` 전부 정확했다.
반면 제품명·인명은 자모 단위로 틀린다.

→ **설계 입력**: 전사 교정 UI에서 숫자보다 **고유명사 강조를 우선**해야 한다.
`review-contract.md` 전사문 루브릭 #2("중요한 이름·숫자·날짜가 정확한가?")에서
실제 위험은 **이름 쪽**에 몰려 있다.

### 7.3 결정 사항 — 재현율 2/2 · 오탐 0/3

| 항목 | 기대 | 실제 | 판정 |

### 7.5 🔑 핵심 발견 — 화자 분리 없이는 1인칭 담당자를 채울 수 없다

A1의 담당자가 `미입력`으로 나온 원인:

```
[seg045] 계약서는 제가 금요일까지 검토해서 공유 드릴게요.      ← "제가"  → 담당자 못 채움

```

**전사문에 화자 라벨이 없으므로 "제가"가 누군지 알 방법이 없다.
모델이 추측하지 않은 것은 실패가 아니라 규칙을 정확히 지킨 것이다.**

→ **제품 설계 결론**: 화자 분리는 "있으면 좋은 것"이 아니라
**1인칭으로 선언된 Action Item의 담당자를 채우는 유일한 수단**이다.
온라인 모드의 `-di` 채널 분리가 붙으면 "제가"를 최소한 `나` vs `원격`으로 해석할 수 있다.
`review-contract.md`가 "결정·Action Item 근거의 화자는 반드시 사람이 확인한다"고 한 조항의
실질적 이유가 실측으로 드러났다.

## 8. 추가 실측 (3차) — 블로커 없이 진행 가능한 항목

### 8.1 🎯 고유명사 initial prompt 주입 — 정확도 57% → 90%

`whisper-cli --prompt` + `--carry-initial-prompt`로 참석자·제품명을 전사 **전에** 주입.

```bash
whisper-cli -m ggml-large-v3-turbo.bin -f meeting-16k.wav -l ko -oj \
  --prompt "회의 참석자는 김민수, 박지영, 이한결입니다. 논의 대상은 토스페이먼츠, 나이스페이, 그라파나, 라따뚜이 결제 모듈입니다." \
  --carry-initial-prompt
```

| 대상 | 기존 (정확/오류) | 주입 후 | 변화 |
| --- | --- | --- | --- |
| 토스페이먼츠 | 2 / **5** | **6 / 0** | ✅ 완전 해결 |
| 그라파나 | 0 / **2** | **2 / 0** | ✅ 완전 해결 |
| 이한결 | 2 / 2 | 2 / 2 | — 동일 |
| 나이스페이·라따뚜이·김민수·박지영 | 8 / 0 | 8 / 0 | — 이미 정확 |
| **고유명사 정확도** | **57.1%** | **90.0%** | **+32.9%p** |
| 숫자·날짜 12종 | 12 / 0 | **12 / 0** | ✅ 회귀 없음 |
| 전사 소요 | 47.2초 | 38.8초 | — |

`이한결`이 안 고쳐진 원인: 원 발화가 **"한결씨"**(호칭형)인데 프롬프트에는 `이한결`만 넣었다.
프롬프트에 호칭형(`한결씨`, `지영씨`)을 같이 넣으면 잡힐 가능성이 높다 — 미검증.

> 🎯 **`technical-foundation.md` 6절이 요구한 검증에 대한 답이다.**
> 문서는 *"필수 입력이 품질을 실제로 개선하는지는 run history로 검증한 뒤 별도 제품 결정으로 도입한다"*고
> 유보했다. **개선한다. 그것도 크게.**
>
> → **제품 설계 변경 제안**: 참석자·프로젝트명을 **전사 전에** 받아 initial prompt로 주입한다.
> 현재 계약은 입력 정보를 결과 화면(페이지 B)에서 편집하게 되어 있는데, 전사 정확도를 위해서는
> **녹음 시작 전 또는 전사 실행 전**에 받아야 효과가 있다. 단, `technical-foundation.md`가
> "필수 gate로 만들지 않는다"고 한 원칙은 유지할 수 있다 — 비어 있으면 프롬프트 없이 전사하면 된다.

### 8.2 ✅ `-di` 채널 화자 분리 — 98.2% 정확

실제 2트랙 녹음이 없어 **정답을 아는 합성 파일**로 메커니즘을 검증했다.

- 합성: `0~150초 = 왼쪽 채널만` + `150~300초 = 오른쪽 채널만` (반대쪽은 무음)
- L-R 채널 차이 -15.7dB (모노성 파일은 -36~-52dB)

| 구간 | 정답 | 판정된 speaker |
| --- | --- | --- |
| 0~150초 (L) | 화자 A | **speaker 0** — 15/16 |
| 150~300초 (R) | 화자 B | **speaker 1** — 39/39 |

**세그먼트 정확도 54/55 = 98.2%, 불확실(`?`) 0건.**

JSON 출력에 `speaker` 필드가 추가된다:

```json
{"timestamps": {...}, "offsets": {...}, "text": "...", "speaker": "0"}
```

→ **온라인 회의에서 `mic.webm`과 `remote.webm`을 좌/우 채널로 합치면
`나` vs `원격`이 기계적으로 분리된다는 설계가 실증됐다.**

**미검증**: 이 합성에는 **말겹침이 없다**(한쪽이 말할 때 반대쪽은 완전 무음).
실제 회의의 동시 발화 구간에서 어떻게 판정하는지는 실제 2트랙 녹음으로 확인해야 한다.

### 8.3 ❌ 결정적 발견 — Hermes STT는 timestamp를 반환할 수 없다

`stt.provider: local_command`로 "hermes로만 전사"를 검증하려 했으나, **구조적으로 불가능**함을 확인했다.

**경로별 확인 결과**

| 경로 | timestamp | 근거 |
| --- | --- | --- |
| `local` (faster-whisper) | ❌ | `_join_confident_segments(segments, ...)` — faster-whisper가 준 segment를 **문자열로 합침**. 반환은 `{"success", "transcript": str, "provider"}` |
| `local_command` | ❌ | `txt_files = sorted(Path(output_dir).glob("*.txt"))` → **`.txt`만 읽음.** `-oj`로 JSON을 써도 무시됨 |
| **플러그인 provider ABC** | ❌ | Response contract가 `transcript: str` **단일 필드**. timestamp를 담을 슬롯이 인터페이스에 없음 |
| `POST /api/audio/transcribe` (`hermes serve`) | ❌ | `transcribe_recording` → 같은 경로. 게다가 base64 업로드 **25MB 제한** |

**모든 경로가 평문 문자열만 반환한다. 설정 문제가 아니라 인터페이스 설계다.**

**추가 제약**

| 제약 | 값 | 영향 |
| --- | --- | --- |
| `subprocess.run(timeout=...)` | **300초** | 1시간 회의는 전사에 약 5분 소요 → 아슬아슬 |
| HTTP 업로드 상한 | **25MB** | 10분 회의(14MB)는 base64로 19MB, 30분 회의는 초과 |
| `shlex.split(command)` | 셸 없음 | `&&`·파이프 불가, wrapper 스크립트 필요 |
| `stt` 툴셋 | **에이전트 도구 아님** | `hermes -z ... -t stt` → `ignoring unknown --toolsets entries: stt`. 용도는 "gateway voice messages + voice mode" |

**Hermes STT는 "짧은 음성 메시지 → 텍스트" 용도로 설계됐다. 회의 녹음 전사용이 아니다.**

**제품 요구사항과의 충돌**

| 문서 | 요구 |
| --- | --- |
| `technical-foundation.md` 3절 | "출력은 timestamp가 포함된 **구조화 JSON**" |
| `review-contract.md` 단계 A-4 | "timestamp를 누르면 해당 음성을 **바로 들을 수 있어야** 한다" |
| `review-contract.md` 원문 근거 | "evidence segment ID와 **timestamp**" |

timestamp는 **선택이 아니라 필수 계약**이다.

→ **결론: "hermes로만 전사"는 성립하지 않는다.**

**권장 구조** — 모델 경계는 Hermes가 소유하되 전사만 분리

```text
Ratatouille 서버
  ├─ whisper-cli 직접 호출     → timestamp JSON + speaker 라벨 확보
  │    (사용자 입력 정보를 --prompt로 주입, 온라인 모드는 -di)
  └─ Hermes ratatouille profile → 4개 결과 생성 (hermes -z, 검증됨)
       └─ openai-codex OAuth
```

**이것은 `technical-foundation.md` 2절의 원래 소유권 그림과 정확히 일치한다.**
문서가 `whisper.cpp`를 전사 소유자로 둔 것이 옳았다.
Hermes는 **모델 경계**를 소유하고, `whisper.cpp`는 **전사 엔진**을 소유한다.
