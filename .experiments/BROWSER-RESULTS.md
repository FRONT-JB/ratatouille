# Phase 0.1~0.4 브라우저 수집 실측

**측정일**: 2026-08-05
**환경**: Chrome 151 (headless, Playwright) · macOS · M4 Mac mini 32GB
**하니스**: [`browser/harness.html`](browser/harness.html)
**방법**: 실제 마이크 대신 Web Audio(`OscillatorNode` → `MediaStreamAudioDestinationNode`)로
합성 스트림을 만들어 측정했다. 결정론적이라 재현 가능하다.

> ⚠️ **합성 스트림의 한계**: 실제 마이크는 무음 구간·잡음·가변 비트레이트가 있어
> 조각 크기 분포가 더 넓다. 아래 수치는 **상한이 아니라 기준선**이다.

## 0.2 MediaRecorder chunk 길이 — **5초 권장**

30초 녹음 × 3개 설정.

| timeslice | 조각 수 | 총 바이트 | 평균 조각 | 최소~최대 | gap 평균 | gap 최대 | stop 지연 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **1초** | 30 | 482,659 | 16,089 B | 7,743~16,438 | 1,000 ms | 1,025 ms | **0 ms** |
| **5초** | 6 | 483,241 | 80,540 B | 78,261~81,160 | 4,992 ms | 5,041 ms | **0 ms** |
| **10초** | 3 | 483,193 | 161,064 B | 160,518~161,338 | 9,990 ms | 10,021 ms | **0 ms** |

**관측**

- **비트레이트는 chunk 길이와 무관하게 일정하다** — 16.1 KB/s ≈ 129 kbps.
  세 설정의 총 바이트 차이가 0.12% 이내다. 즉 **조각을 잘게 쪼개도 오버헤드가 사실상 없다.**
- **gap 정확도가 높다** — 목표 대비 최대 편차 25~41 ms.
- **`stop()` 지연이 0 ms** — 마지막 조각이 즉시 도착한다. 종료 시 유실 위험이 낮다.
- 마지막 조각은 항상 작다(부분 구간). 첫 조각에는 webm 헤더가 들어간다.

**30분 녹음 외삽**

| timeslice | 조각 수 | 총 용량 |
| --- | --- | --- |
| 1초 | 1,800 | 29 MB |
| **5초** | **360** | **29 MB** |
| 10초 | 180 | 29 MB |

**결론: 5초.** 근거는 크기가 아니라 **유실 노출량**이다.

- 조각 오버헤드가 없으므로 큰 조각을 쓸 이유가 없다.
- 브라우저가 죽으면 **아직 flush 되지 않은 구간**을 잃는다.
  1초는 유실 노출이 가장 적지만 30분에 조각 1,800개 → 서버 검증·manifest가 비대해진다.
  10초는 조각 수는 적지만 크래시 시 최대 10초를 잃는다.
- 5초는 유실 상한 5초, 조각 360개로 균형점이다.

## 0.1 로컬 저장소 — **IndexedDB 권장**

30분 녹음에 해당하는 360개 × 80,540 B(= 실측 5초 조각) 쓰기/읽기.

| | 쓰기 | 읽기 | 쓰기 처리량 |
| --- | --- | --- | --- |
| **IndexedDB** | **65 ms** | 28 ms | **422.8 MB/s** |
| OPFS | 244 ms | 36 ms | 113.1 MB/s |

**IndexedDB가 쓰기에서 3.7배 빠르다.**

원인은 API 형태다. IndexedDB는 **한 트랜잭션에 360건을 넣고 한 번 commit**하지만,
OPFS는 파일마다 `getFileHandle` → `createWritable` → `write` → `close` 4번의 await가 필요하다.
파일당 왕복 비용이 누적된다.

> OPFS에는 동기 접근(`createSyncAccessHandle`)이 있고 Worker에서 쓰면 훨씬 빨라진다.
> 이번 측정은 **메인 스레드 비동기 API 기준**이다. Worker 기반 OPFS는 미측정이다.

**결정: IndexedDB**

- 30분 분량 전체를 쓰는 데 65 ms — 5초마다 한 조각씩 쓰는 실제 부하는 무시할 수준이다
- 할당량 10 GB로 29 MB짜리 30분 녹음이 **수백 개** 들어간다
- 트랜잭션 단위 원자성이 조각 무결성에 유리하다

**필수 후속 조치**: `navigator.storage.persisted()`가 `false`다.
디스크 압박 시 브라우저가 데이터를 **말없이 evict** 할 수 있다.
녹음 시작 전에 `navigator.storage.persist()`를 반드시 호출해야 한다.

## 0.3 재전송 protocol — hash 비용은 무시 가능

| 항목 | 값 |
| --- | --- |
| SHA-256 × 360 조각 (80.5 KB each) | **10 ms 총합** |
| 조각당 | **0.03 ms** |
| 처리량 | 2,821 MB/s |

`crypto.subtle.digest`가 사실상 공짜다. **모든 조각에 SHA-256을 붙여도 비용이 없다.**

→ 재전송 protocol에서 조각별 hash 검증을 **주저 없이 채택한다.**
`technical-foundation.md` 4절의 "서버는 순번, 크기와 hash를 확인한다"가 성능상 부담이 아니다.

**하니스에서 발견한 구현 주의점**: `crypto.getRandomValues`는 호출당 **65,536 바이트 상한**이다.
80 KB 조각을 한 번에 채우려다 `QuotaExceededError`가 났다. 64 KB씩 나눠 호출해야 한다.
(테스트 데이터 생성에만 해당 — 실제 녹음 조각에는 무관)

## 0.4 mic / remote 시간축 정렬 — **일시정지가 유일한 위험**

두 `MediaRecorder`를 같은 tick에서 시작하고, 30초 중 절반 지점에서 A만 400 ms 일시정지 후 재개.

| 항목 | 값 |
| --- | --- |
| `start()` 호출 간격 | **0.1 ms** |
| 첫 조각 도착 시각 차이 | **0 ms** |
| 마지막 조각 도착 시각 차이 | **0 ms** |
| 조각 수 | A=6, B=7 (**A가 1개 적음**) |
| 최대 절대 편차 | **295.3 ms** |

**관측**

- **정상 구간에서는 정렬이 완벽하다.** 두 recorder를 같은 tick에서 시작하면
  첫 조각과 마지막 조각이 0 ms 차이로 도착한다. 초기 오프셋 보정이 필요 없다.
- **일시정지가 드리프트를 만든다.** A를 400 ms 멈췄더니 조각이 1개 적게 생기고
  최대 295 ms까지 어긋났다. `MediaRecorder.pause()`는 **타임라인 자체를 멈춘다** —
  재개 후 A의 미디어 시각은 실제 벽시계보다 뒤처진다.

**설계 결론**

1. **두 track을 같은 tick에서 시작한다.** 이것만으로 초기 정렬이 해결된다.
2. **일시정지는 반드시 두 recorder에 동시에 적용한다.** 한쪽만 멈추면 어긋난다.
   페이지 A의 `일시정지` 버튼은 mic·tab 양쪽을 함께 제어해야 한다.
3. **manifest에 각 track의 조각 수와 일시정지 구간을 기록한다.**
   조각 수 불일치 자체가 정렬 이상 신호다.
4. 입력 단절로 한쪽 track만 끊긴 경우도 같은 증상이 난다 —
   `PLAN.md` 순서 2의 "마이크만 끊은 경우와 탭 오디오만 끊은 경우를 다르게 표시"가
   정렬 무결성 관점에서도 필요하다.

> `-di` 채널 화자 분리(`RESULTS.md` 8.2절)를 쓰려면 두 track을 좌/우로 **병합**해야 한다.
> 정렬이 어긋나면 화자 라벨도 어긋난다. 위 3개 규칙이 화자 분리의 전제 조건이다.

## 미검증 항목

- **실제 마이크·탭 오디오** — 합성 스트림 기준이다. 무음 구간과 가변 비트레이트에서
  조각 크기 분포가 달라질 수 있다
- **30분 연속 녹음** — 30초 측정의 선형 외삽이다. 장시간 메모리 증가와 IndexedDB
  트랜잭션 지연 누적은 확인하지 않았다
- **브라우저 강제 종료 후 잔존** — IndexedDB에 남은 조각을 복구하는 경로를 시험하지 않았다
- **Worker 기반 OPFS(`createSyncAccessHandle`)** — 메인 스레드 비동기 API만 측정했다.
  IndexedDB를 뒤집을 만큼 빠를 가능성이 있다
- **네트워크 중단 중 로컬 축적** — 업로드가 막힌 동안 IndexedDB가 얼마나 버티는지
- **탭 백그라운드 throttling** — 다른 탭으로 전환했을 때 타이머·녹음이 유지되는지
